# USA.gov Backup System Documentation

## Overview

The USA.gov backup system provides comprehensive automated backups for:

- Static site files (generated by Tome)
- Public CMS files (uploads, assets)
- Database dumps

Backups are stored in AWS S3 with configurable retention periods and automatic cleanup.

## Architecture

### Components

1. **Static Site & Public File Backups**
   - Integrated with Tome static site generation
   - Smart backup system that only backs up when content changes
   - Triggered automatically on every successful Tome sync

2. **Database Backups**
   - Scheduled daily backups via cron
   - Independent of Tome runs
   - Uses existing database snapshot infrastructure

3. **Backup Management**
   - Unified management interface for all backup types
   - List, clean, restore, and info commands
   - Automatic cleanup of old backups

### Storage Structure

```
S3 Bucket/
├── web-backup/          # Static site backups
│   └── AUTO-{space}-{timestamp}/
├── public_backup/       # Public file backups
│   └── AUTO-{space}-{timestamp}/
└── database/           # Database backups
    └── DB-AUTO-{space}-{timestamp}.sql.gz
```

## Configuration

All backup settings are configured in `scripts/auto-backup-system.conf`:

### Static Site & Public File Settings

```bash
# Enable/disable automatic backups during Tome runs
ENABLE_STATIC_AUTO_BACKUPS=true
ENABLE_PUBLIC_AUTO_BACKUPS=true

# Enable smart public file backup (only when changes detected)
ENABLE_SMART_PUBLIC_BACKUP=true

# Automatic cleanup of old backups
ENABLE_STATIC_AUTO_CLEANUP=true
ENABLE_PUBLIC_AUTO_CLEANUP=true

# How many days to keep backups
BACKUP_RETENTION_DAYS=7

# Prefix for backup directories
BACKUP_PREFIX="AUTO"
```

### Database Backup Settings

```bash
# Enable/disable daily database backups
ENABLE_DB_BACKUPS=true

# Time to run daily backups (24-hour format, EST)
DB_BACKUP_TIME="19:00"

# How many days to keep database backups
DB_BACKUP_RETENTION_DAYS=30

# Prefix for database backup files
DB_BACKUP_PREFIX="DB-AUTO"
```

## Usage

### Static Site & Public File Backups

These backups happen automatically during Tome runs. No manual intervention required.

**Monitor backup creation:**
```bash
# Check Tome sync logs for backup messages
./bin/tome-sync

# List all backups
./scripts/tome-backup-manager.sh list
```

### Database Backups

#### Setup Daily Backups

Run once to set up the cron job:
```bash
./scripts/setup-db-backup-cron.sh
```

**CMS Container Integration:** The setup script automatically detects if you're running in the CMS container (which already has a cron system running for Tome static site generation). In this case, it integrates with the existing Alpine cron system by creating `/etc/periodic/1min/database-backup` that checks the time every minute and only runs the backup at 7pm EST.

**Other Environments:** For local development or other Cloud Foundry containers, it creates a standard crontab entry.

#### Manual Database Backup

Create an immediate database backup:
```bash
./scripts/tome-backup-manager.sh backup-db
```

### Backup Management

#### List Backups

```bash
# List all static site & public file backups
./scripts/tome-backup-manager.sh list

# List all database backups
./scripts/tome-backup-manager.sh list-db
```

#### List Old Backups

```bash
# List static site backups older than 14 days
./scripts/tome-backup-manager.sh list-old 14

# List database backups older than 60 days
./scripts/tome-backup-manager.sh list-db-old 60
```

#### Clean Old Backups

```bash
# Remove static site backups older than 30 days
./scripts/tome-backup-manager.sh clean 30

# Remove database backups older than 90 days
./scripts/tome-backup-manager.sh clean-db 90
```

#### Get Backup Information

```bash
# Get info about a specific static site backup
./scripts/tome-backup-manager.sh info AUTO-dev-2024_03_15_14_30_00

# Get info about a specific database backup
./scripts/tome-backup-manager.sh info-db DB-AUTO-dev-2024_03_15_19_00_00
```

#### Restore from Backup

```bash
# Restore static site and public files from backup
./scripts/tome-backup-manager.sh restore AUTO-dev-2024_03_15_14_30_00
```

**⚠️ Warning:** Restore operations will overwrite current files. Always verify the backup timestamp before restoring.

### Backup Manager Help

```bash
# Show all available commands
./scripts/tome-backup-manager.sh
```

## Monitoring

### Logs

Backup operations are logged to `/tmp/tome-log/backup-YYYY-MM-DD.log`

**View recent backup activity:**
```bash
# Today's backup log
tail -f /tmp/tome-log/backup-$(date +%Y-%m-%d).log

# Recent backup logs
ls -la /tmp/tome-log/backup-*.log
```

### Backup Status

**Check if backups are being created:**
```bash
# List recent backups
./scripts/tome-backup-manager.sh list | head -10
./scripts/tome-backup-manager.sh list-db | head -10
```

**Verify cron job is set up:**
```bash
# Check crontab
crontab -l | grep db-backup

# Check Cloud Foundry cron directory (if applicable)
ls -la /var/vcap/jobs/*/config/cron/
```

## Troubleshooting

### Test the System

Run the comprehensive test suite:
```bash
./scripts/test-backup-system.sh
```

This tests all components and will identify any issues.

#### Force Backup Testing

You can also force immediate backups for testing purposes:

```bash
# Test + force static site backup
./scripts/test-backup-system.sh --force-static-backup

# Test + force public files backup  
./scripts/test-backup-system.sh --force-public-backup

# Test + force database backup
./scripts/test-backup-system.sh --force-db-backup

# Test + force all three backup types
./scripts/test-backup-system.sh --force-all-backups

# Show all available options
./scripts/test-backup-system.sh --help
```

**Note:** Forced backups require proper S3 credentials and configuration. They will create actual backups in your S3 bucket, so use with caution in production environments.

### Common Issues

1. **AWS credentials not available**
   - Ensure VCAP_SERVICES contains S3 credentials (Cloud Foundry)
   - Or set AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY

2. **Backup not triggered during Tome sync**
   - Check that `ENABLE_STATIC_AUTO_BACKUPS=true` and `ENABLE_PUBLIC_AUTO_BACKUPS=true` in auto-backup-system.conf
   - Verify tome-sync.sh completed successfully
   - Check backup logs for error messages

3. **Database backups not running**
   - Verify cron job is set up: `crontab -l`
   - Check that `ENABLE_DB_BACKUPS=true` in auto-backup-system.conf
   - Ensure db-dump-to-snapshot script is available
   - Check database backup logs

4. **Old backups not being cleaned up**
   - Verify `AUTO_CLEANUP_STATIC=true` and `AUTO_CLEANUP_DB=true` in auto-backup-system.conf
   - Check retention day settings
   - Manually run cleanup: `./scripts/tome-backup-manager.sh clean`

5. **Shell compatibility issues**
   - Scripts are designed for POSIX shell (/bin/sh)
   - Avoid bash-specific features in Cloud Foundry
   - Test with: `sh ./scripts/script-name.sh`

### Log Analysis

**Check for backup failures:**
```bash
grep -i error /tmp/tome-log/backup-*.log
```

**Monitor backup sizes:**
```bash
./scripts/tome-backup-manager.sh list | grep -E "MB|GB"
```

**Verify smart backup is working:**
```bash
# Should show "No changes detected" when content hasn't changed
grep "No changes detected" /tmp/tome-log/backup-*.log
```

## Environment-Specific Notes

### Cloud Foundry

- Uses VCAP_SERVICES for AWS credentials
- Uses `/bin/sh` (not bash)
- Limited disk space for temporary files

**CMS Container Cron Integration:**
- The CMS container already runs Alpine cron with `/etc/periodic/1min/generate-static-site`
- Database backup integrates with this existing system
- Creates `/etc/periodic/1min/database-backup` that checks time every minute
- Only runs backup at configured time (7pm EST by default)
- Respects `CF_INSTANCE_INDEX=0` constraint (only first instance runs cron)
- No additional crontab entries needed

### Local Development

- Requires AWS CLI configuration
- Uses standard cron for scheduling
- Can use bash or sh

### CircleCI

- Static site backups work with existing CI/CD
- Database backups are separate from deployment
- Uses environment variables for AWS access

## Security Considerations

1. **Credentials**
   - AWS credentials are read from VCAP_SERVICES or environment
   - Never store credentials in code or logs

2. **Access Control**
   - Backup scripts should only be executable by authorized users
   - S3 bucket access should be restricted

3. **Data Sensitivity**
   - Database backups may contain sensitive information
   - Consider encryption for highly sensitive data

## Performance

### Impact on Tome Runs

- Smart backup only creates backups when content changes
- Backup creation adds ~30-60 seconds to Tome sync
- Uses md5sum for change detection to minimize overhead

### Storage Costs

- Configure retention periods appropriately
- Monitor S3 storage usage
- Use automatic cleanup to prevent accumulation

### Network Usage

- Backups upload to S3 during Tome runs
- Database backups happen separately (daily)
- Failed uploads are retried automatically
